meta-styles — a wardrobe that styles back, in chat

A public guide to meta-styles, an entry to the Meta Global AI Developer Hackathon (Indie Developer track). It is a persistent, per-user wardrobe and catalogue built from shared photos, with a chat interface, fit-rule validation, and an agentic loop that proposes, validates, and revises looks.

What meta-styles is

Share photos of garments and meta-styles catalogues each piece into your own persistent wardrobe. Then, in an Instagram-DM-style chat thread, it puts together complete looks from what you already own, explains why a look works, and suggests a single next purchase when something is missing. The emphasis is on full-look assembly for real bodies and second-hand-first sourcing — not on classifying one photo in isolation.

Every turn runs through an agentic loop. A router picks one of eleven skills (catalogue a piece, propose or revise a look, explain the fit, evaluate a possible purchase, and others). Each proposed look is checked against explicit fit rules — a base plus exactly one finish, with invalid layering rejected — before you ever see it. If confidence is low, the agent asks a clarifying question instead of guessing. If you push back (“without the blazer”), it re-proposes minus that piece and re-validates. Low-confidence or off-topic messages get a friendly deflection with a pointer back to this guide.

Running the judged demo

The judged path is a local one-shot install and run. Your only requirement is your own Meta API key — no other account, credential, or hosted service is needed. From the repo root, with your key in the environment:

MODEL_API_KEY=<your-meta-api-key> sh start.sh

Then open http://localhost:8000/mock-dm.html in a browser on the same machine. That page is the judged chat surface: an inbox thread plus operator panels. A three-step walkthrough (share a dress, share a layer, get one purchase suggestion) is in the repository README.

The default demo uses synthetic mock-DM data (fixtures with SYNTH_ ids) and local-only services: a Meta-model proxy, a mock DM bot, and a static server, all on your machine. Meta model calls always use your own key, which travels in the process environment only and is never written into source, commits, or logs. Without a key the demo still starts and runs on clearly labelled stub and cached fallbacks.

Honest limits

  • No invented details. Asked about fabric, price, or vendor, the agent says plainly it does not hold that data. It never invents a listing.
  • Preview may be unavailable on fallback. Without model access there is no AI-rendered preview; the app shows a simple collage instead, and says so.
  • Real Instagram mode is local-only and not the judged path. A live-bot mode exists but works only on the machine already running that bot, and real sends fire solely on explicit user clicks. Judges should use the mock path above.
  • There is no hosted live demo. Delivery is the local install-and-run above, not a public URL.

Project boundary: prior work stays prior work

Some Instagram plumbing behind this project — the SecondBloom DM-share receiver and its local read, catalog, and send routes — was built and deployed in mid-October 2026, before the hackathon build window opened. It is documented as prior work in docs/prior-work-instagram.md and is not claimed as hackathon-built. Only the meta-styles-side client and integration code in this repo is new work from the hackathon window. Anything the older service feeds the app works only on the machine running that service; elsewhere the app falls back cleanly to synthetic fixtures.
